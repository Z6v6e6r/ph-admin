# Критические сценарии перехода Viva → ЦУП

Реестр содержит 28 сценариев. `P0` означает, что без доказанного parity/replacement cutover соответствующего домена запрещён. Статус всех строк на старте — `DISCOVERY`.

## Обязательный E2E-паспорт сценария

Для каждого `SC-*` создаётся одна карточка со следующими разделами:

1. Business owner, операторские роли, станции и частота выполнения.
2. Trigger, preconditions, входные данные и источник identity.
3. Пошаговый текущий путь в Viva с видео и audit evidence.
4. Текущий путь в ЦУП, если он существует, с API/DB evidence.
5. Canonical aggregates и единственный writer на каждом шаге.
6. Деньги: amount, currency, discount, tax, provider, receipt, settlement.
7. События/webhooks, порядок, event ID, aggregate version и watermark.
8. Happy path и минимум три отказа: timeout, duplicate/retry, частичное выполнение.
9. Компенсация/repair, права на выполнение и неизменяемый audit.
10. Отчёты и projections, в которых должен появиться результат, включая допустимую задержку.
11. PII/consent/retention и station/tenant isolation.
12. Acceptance evidence и подписи Operations/Product/Finance/Engineering по применимости.

## Общие acceptance checks

Каждый P0-сценарий должен доказать:

- повтор команды с тем же idempotency key не создаёт второй бизнес-эффект;
- конкурентные действия либо сериализованы версией агрегата, либо дают явный конфликт;
- ошибка между записью состояния и публикацией события восстанавливается через transactional outbox;
- audit содержит actor, роль, station/tenant, before/after, reason, correlation ID и timestamp;
- невозможно выполнить действие вне station/tenant scope;
- projection lag виден, измерим и не выдаётся за canonical состояние;
- есть reconciliation query и процедура repair без ручной правки production-БД;
- даты/время проверены на локальную timezone, UTC и переходы суток;
- персональные и финансовые данные маскируются в логах;
- оператор понимает, где продолжить работу при недоступности Viva, ЦУП или провайдера.

## Приоритет walkthrough

Первые пять записей экрана должны пройти цепочками, а не отдельными функциями:

1. `SC-01 → SC-04 → SC-05 → SC-12 → SC-27`.
2. `SC-05 → SC-06 → SC-07`.
3. `SC-05 → SC-08 → SC-20 → SC-21`.
4. `SC-10 → SC-11 → SC-19`.
5. `SC-15 → SC-16 → SC-17 → SC-18`.

После walkthrough владелец помечает сценарий одним из статусов: `AS_IS_CAPTURED`, `TARGET_DEFINED`, `CONTRACT_PROVEN`, `E2E_PROVEN`, `APPROVED`. Переход к этапу 1 требует `APPROVED` для всех P0 либо формально утверждённого исключения с датой окончания.
