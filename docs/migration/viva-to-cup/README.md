# Этап 0 перехода Viva → ЦУП

Статус: `STARTED`
Окно: 20 июля — 28 августа 2026 года (4 недели при полном доступе к Viva с первой недели, базовый план — 6 недель)
Цель: получить утверждённую и доказуемую границу миграции до начала переноса бизнес-логики и данных.

## Что считается результатом

Этап 0 завершён только когда одновременно выполнены все условия:

1. Фактический реестр Viva покрывает экраны, API, данные, фоновые задачи, ручные действия, отчёты, платежи, подписки и интеграции.
2. Для каждого элемента реестра есть владелец, источник доказательства, дата проверки и решение: переносить, заменить, оставить внешним или вывести из эксплуатации.
3. Не менее 20 и не более 30 критических сценариев разобраны end-to-end, включая ошибки, повтор запроса, аудит, восстановление и сверку.
4. Для каждого P0-агрегата назначен ровно один текущий и один целевой writer. Не осталось `UNDECIDED` по ownership.
5. API/export/webhook-доступ Viva зафиксирован документом, проверен в sandbox и содержит версии, лимиты, SLA, идемпотентность и правила изменения контракта.
6. В миграционном пути нет UI-скрейпинга, DOM-автоматизации и зависимости от личных учётных записей сотрудников.
7. Прямой штатный доступ сотрудников к Viva закрыт; break-glass проверен учебным инцидентом и оставляет полный аудит.
8. Operations, Product, Finance, Support, Security, Data и Engineering подписали решение `GO TO STAGE 1` либо зафиксировали `NO-GO` с владельцами и сроками закрытия.

## Доказательность

Используется следующая шкала:

| Статус | Значение |
|---|---|
| `FACT_REPO` | Подтверждено текущим checkout, но не доказывает работу production |
| `FACT_RUNTIME` | Подтверждено запросом, логом, БД или браузером в указанном окружении |
| `FACT_VIVA` | Подтверждено Viva: договором, официальной спецификацией, export или совместным тестом |
| `ASSUMPTION` | Рабочая гипотеза; нельзя использовать для проектирования cutover |
| `DECISION_REQUIRED` | Требуется решение владельцев |
| `APPROVED` | Решение подписано перечисленными ролями |

Скриншот без роли, URL, времени и описанного действия не считается достаточным доказательством. Код адаптера не считается договорённостью с Viva. Production-данные не копируются в документы; используются обезличенные примеры и ссылки на защищённое хранилище доказательств.

## План на 6 недель

| Неделя | Даты | Результат | Обязательные участники |
|---|---|---|---|
| 1 | 20–24 июля | Kickoff, список ролей и площадок, доступы, календарь интервью, место хранения доказательств, первая выгрузка Viva | Product, Operations, Viva, Engineering, Security |
| 2 | 27–31 июля | Walkthrough всех экранов и ручных операций; API/data/integration inventory | Operations, администраторы станций, Support, Engineering |
| 3 | 3–7 августа | Разбор 28 сценариев, платежей, возвратов, подписок и отчётов; профилирование экспортов | Product, Finance, Operations, Data |
| 4 | 10–14 августа | Canonical model v1, identity mapping, ownership matrix, retention и audit requirements | Architecture, Data, Security, Legal |
| 5 | 17–21 августа | Подтверждение API/export/webhook contract, sandbox-пробы, reconciler design, break-glass drill | Viva, Engineering, SRE, Security |
| 6 | 24–28 августа | Закрытие пробелов, подписи, risk register, решение GO/NO-GO для этапа 1 | Все владельцы |

Сжатие до четырёх недель допустимо только если до конца первой недели получены официальный API contract, полный export, sandbox и все владельцы доступны для walkthrough. Уменьшение перечня доказательств ради срока не допускается.

## Ритм управления

- Ежедневно: обновление реестра и блокеров владельцами.
- Дважды в неделю: 45 минут domain walkthrough с записью и протоколом.
- Еженедельно: steering — покрытие реестра, открытые P0, vendor blockers, решения.
- Любое новое знание сначала получает evidence/status, затем может менять canonical model.
- Решение считается принятым только после записи в `decision-log.md`; устная договорённость не меняет ownership.

## Немедленные действия первой недели

1. Назначить людей на все роли выше.
2. Запросить у Viva официальный пакет из раздела «Contract gate».
3. Выбрать 2 станции с разной операционной моделью и по одному сотруднику каждой ключевой роли.
4. Провести первую запись экрана: открытие дня → продажа → запись → перенос → отмена → возврат → закрытие дня.
5. Получить полный обезличенный export и повторный delta-export с watermark.
6. Снять список Viva-аккаунтов и фактических входов за 90 дней; подготовить группы normal и break-glass.
7. Назначить владельца и срок каждому `P0` в реестре и сценариях.
