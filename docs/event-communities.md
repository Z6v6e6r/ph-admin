# Event communities: first corporate-sport pilot

Owner: CUP community managers configure the type; LK/Node-RED owns registration and mini-game results. Audience: authenticated LK members. The user-selected pilot name is **Корпоративный спорт ПадлхАБ**. This source change does not activate a live community.

## Behavior and compatible contract

`EVENT` is the fifth community type. Settings are `{gameIds: ['padel-jump', 'time-for-friends']}`; the nonempty allowlist is validated identically in CUP and LK. Existing types/defaults, settings authorization and optimistic revision updates remain unchanged. CUP's type editor selects the two games. The game links appear on the event feed and its ranking tab.

The existing direct join/add-member and join-by-invite endpoints accept optional `eventRegistration: {fullName, company, email}`. For EVENT it is mandatory before a new member, an existing member after conversion, or a pending member receives successful admission without a stored current-activation registration. The full name accepts surname/name and optional patronymic. A verified profile ID authorizes participation; submitted names/contact data never authorize or identify the caller. Email is collected, not verified, and sends no mail. Existing LK authentication still applies.

Missing/invalid registration returns 422 `EVENT_REGISTRATION_REQUIRED` / `EVENT_REGISTRATION_INVALID`. The frontend opens the same form for normal entry and invitation links, including automatic invite entry. Normal invitation/moderation/ban rules remain enforced. Staff can still moderate members; game access independently requires completed registration and current active membership.

`GET /lk/communities/:communityId/event-game/ranking` returns `{communityId, rows: [{rank, name, score}]}`. It requires current exact-ID membership and registration. Public names come from the existing profile/roster, never the private full-name form. The event ranking is best Padl Jump height, descending; ties use first achievement then stable player ID internally. Removed, banned, inactive, prior-activation and other-engine entries are omitted. A new engine starts its own best-score comparison rather than inheriting an incompatible old record. These points never change sports level, rating_events, tournament outcomes or the generic rating-worker formula.

`POST .../event-game/start` and `POST .../event-game/finish` require a UUID-v4 `Idempotency-Key` and the shared `engineVersion`. Start issues CSPRNG run ID/seed and server time. A retry with the same key returns the same run. Finish accepts its run ID and run-length encoded `[quantizedDirection, fixedTicks]` pairs; client score values are ignored. The browser and server use the same original Jump engine/campaign from source `cb4f1202`, with an exact SHA-256 of those two files checked when building a Node-RED candidate. A changed engine returns 409 rather than silently reinterpreting a run. Game mode for this leaderboard is endless ascent, capped at 300 seconds of simulation.

Only terminal/reaching-the-cap traces are accepted: at most 36,000 ticks, 12,000 segments, 150 KB of JSON, direction integers -100..100. Server wall time rejects accelerated submissions. Replay has a 50ms compute deadline, a 10/sec per-function budget and 30/min per-actor command budget. No trace is stored. Completed-run receipts and the best-run receipt contain run ID, score, engine hash, revision, ticks and server completion time. Same-run completion retries return the committed result. A concurrently changed roster/config/registration returns 409; the client retains an unsent result in page memory and offers explicit retry.

## Private storage and recovery

`lk_communities.eventEntries` is a bounded private array, one entry per verified actor, maximum 500. It stores fullName/company/email, registration time, activation epoch, current run and best result/receipt. `eventEntriesRevision` is a numeric compare-and-set fence. Registering and joining share one community update, including roster preimages, policy revision and the registration revision; game commands fence membership/bans/policy/registration revision. Private entries never appear in Mongo query filters. No new collection/index, migration, startup write, provider write, payment, email or historical backfill is introduced.

Generic public response redaction removes `eventEntries` and form fields even if the community later returns to FRIENDS. CUP raw `details` projections omit the private entries as well. The generic join debug branches do not receive the form; transient registration context is scrubbed from post-commit messages. There is no staff contact export in this change.

Type activation timestamp is the registration/result epoch. Switching away from EVENT and back requires a fresh form and does not republish past scores. Removed/banned actors cannot start/finish or appear in ranking; their private record is preserved for owner-controlled audit/erasure. For this first pilot, **do not reuse an old event community for a new event**. Old entries continue to count toward the 500 cap. Before collecting real data, the owner must establish the registration notice, retention period and authorized erasure process; indefinite reusable contact storage is not accepted by this pilot. No automatic cleanup/backfill is bundled with feature activation.

An unfinished run remains reserved for up to 30 minutes. Closing/reloading and reopening resumes the same seed and run ID rather than allowing seed shopping; a changed policy/engine invalidates the old run. Browser reload also loses an unsent trace; no result is claimed saved until the acknowledged response. This is a pilot UX limitation, not a successful persistence claim.

## First test community and activation prerequisites

`/scripts/fixtures/event-community.json` is synthetic, named **Корпоративный спорт ПадлхАБ**, with the two games already selected. It is a test fixture, not a live import or created production record. A real owner/admin identity, effective server timestamp and live target must be selected at activation. The second game uses the existing same-origin `/padel/` static game. Only Padl Jump contributes to this leaderboard; availability of that second installed game is verified separately at release.

Order: reviewed LK frontend + focused Node-RED candidate, then CUP, then separately authorized activation of the chosen community. Do not enable EVENT against older consumers. Use `node scripts/patch_live_community_types.mjs --input /private/fresh-live.json --out /private/event-candidate.json` only to prepare an external candidate; it does not deploy. The complete hashed change manifest includes event HTTP/auth/database/ack/catch nodes. Both pristine and already-four-type-patched fixtures are covered by upgrade/idempotence tests. The patch refuses unfamiliar roster barriers and missing Mongo4 templates.

Before any live import: verify fresh live graph identity; Mongo4 find/updateOne driver argument and acknowledgement behavior; Node-RED Function `libs` support for the built-in `crypto` module; exact client/server engine hash; and **edge/pre-auth request limits on these routes before the Viva profile subflow**. Replay throttles occur after authentication and do not establish a provider-amplification boundary. This patch does not change routing, expose runtime crypto configuration or claim these target prerequisites have passed.

Import/restart, publication, live creation/configuration and contact-data writes need their explicit target authority. Stop on missing crypto/edge limits/ack, failed identity/privacy checks, unexpected revision conflicts, replay CPU-budget exhaustion or score mismatch. Disable future play by deselecting padel-jump or reverting the type through CUP; preserve private data and best-run receipts for approved recovery. Do not delete entries, rebuild ratings, restore a database or widen permissions as automatic rollback.
