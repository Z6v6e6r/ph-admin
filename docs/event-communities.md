# Event communities: first corporate-sport pilot

Owner: CUP community managers configure the type; LK/Node-RED owns registration and mini-game results. Audience: authenticated LK members. The user-selected pilot name is **Корпоративный спорт ПадлхАБ**. This source change does not activate a live community.

## Behavior and compatible contract

`EVENT` is the fifth community type. Settings include `{gameIds: ['padel-jump', 'time-for-friends']}` and optional `registrationPolicy` (required for admission/play); the nonempty allowlist is validated identically in CUP and LK. Existing types/defaults, settings authorization and optimistic revision updates remain unchanged. CUP's type editor selects the two games. The game links appear on the event feed and its ranking tab.

The existing direct join/add-member and join-by-invite endpoints accept optional `eventRegistration: {fullName, company, email, policyRevision}`. For EVENT it is mandatory before a new member, an existing member after conversion, or a pending member receives successful admission without a stored current-activation registration. The full name accepts surname/name and optional patronymic. A verified profile ID authorizes participation; submitted names/contact data never authorize or identify the caller. Email is collected, not verified, and sends no mail. Existing LK authentication still applies.

Missing/invalid registration returns 422 `EVENT_REGISTRATION_REQUIRED` / `EVENT_REGISTRATION_INVALID`. The frontend opens the same form for normal entry and invitation links, including automatic invite entry. Normal invitation/moderation/ban rules remain enforced. Staff can still moderate members; game access independently requires completed registration and current active membership.

`GET /lk/communities/:communityId/event-game/ranking` returns `{communityId, rows: [{rank, name, score}]}`. It requires current exact-ID membership and registration. Public names come from the existing profile/roster, never the private full-name form. The event ranking is best Padl Jump height, descending; ties use first achievement then stable player ID internally. Removed, banned, inactive, prior-activation and other-engine entries are omitted. A new engine starts its own best-score comparison rather than inheriting an incompatible old record. These points never change sports level, rating_events, tournament outcomes or the generic rating-worker formula.

`POST .../event-game/start` and `POST .../event-game/finish` require a UUID-v4 `Idempotency-Key` and the shared `engineVersion`. Start issues CSPRNG run ID/seed and server time. A retry with the same key returns the same run. Finish accepts its run ID and run-length encoded `[quantizedDirection, fixedTicks]` pairs; client score values are ignored. The browser and server use the same original Jump engine/campaign from source `cb4f1202`, with an exact SHA-256 of those two files checked when building a Node-RED candidate. A changed engine returns 409 rather than silently reinterpreting a run. Game mode for this leaderboard is endless ascent, capped at 300 seconds of simulation.

Only terminal/reaching-the-cap traces are accepted: at most 36,000 ticks, 12,000 segments, 150 KB of JSON, direction integers -100..100. Server wall time rejects accelerated submissions. Replay has a 50ms compute deadline, a 10/sec per-function budget and 30/min per-actor command budget. No trace is stored. Completed-run receipts and the best-run receipt contain run ID, score, engine hash, revision, ticks and server completion time. Same-run completion retries return the committed result. A concurrently changed roster/config/registration returns 409; matchedCount=1 plus acknowledged=true plus modifiedCount=1 is required for real mutation success; the client retains an unsent result in page memory and offers explicit retry.

## Private storage and recovery

`lk_communities.eventEntries` is a bounded private array, one entry per verified actor, maximum 500. It stores fullName/company/email, server registration time, activation epoch, accepted policy revision/version, server-derived retention deadline, current run and best result/receipt. `eventEntriesRevision` is a numeric compare-and-set fence. Registering and joining share one community update, including numeric EVENT roster/policy/registration revisions. EVENT game and roster filters contain no member/contact arrays; `eventRosterRevision` is incremented by every LK join/invite/member-management writer and CUP moderation writer. Station autojoin never enrolls EVENT. Legacy TIME_FOR_FRIENDS worker/operator planners quarantine EVENT, and their atomic mutation filters exclude EVENT even if conversion races with a prepared plan. Ship these helper/worker inputs before activation. Type/config changes are fenced so stale non-EVENT moderation cannot bypass the revision after conversion. Private entries never appear in Mongo query filters. Missing EVENT roster revision is treated as an uninitialized numeric fence until the first acknowledged mutation; there is no bulk backfill. All participating writers must be upgraded before activation. No new collection/index, startup write, provider write, payment, email or historical backfill is introduced.

Generic public response redaction removes `eventEntries` and form fields even if the community later returns to FRIENDS. CUP raw `details` projections omit the private entries as well. The generic join debug branches do not receive the form; transient registration context is scrubbed from post-commit messages. There is no staff contact export in this change.

Type activation timestamp is the registration/result epoch. Switching away from EVENT and back requires a fresh form and does not republish past scores. Removed/banned actors cannot start/finish or appear in ranking; their private record is preserved for owner-controlled audit/erasure. For this first pilot, **do not reuse an old event community for a new event**. Old entries continue to count toward the 500 cap. Admission/play require the complete versioned notice described below. No automatic cleanup/backfill runs on startup. The offline erasure planner and the responsible operator provide the deletion procedure; the one-year deadline must be put into the operator calendar before collecting real data.

An unfinished run remains reserved for up to 30 minutes. Closing/reloading and reopening resumes the same seed and run ID rather than allowing seed shopping; a changed policy/engine invalidates the old run. Browser reload also loses an unsent trace; no result is claimed saved until the acknowledged response. This is a pilot UX limitation, not a successful persistence claim.

## Registration policy and timing

`typeSettings.registrationPolicy` is optional for saving a draft EVENT, but mandatory for all admission and game commands. Its exact keys are `version: 'event-registration-v1'`, `responsibleName`, `contactEmail`, canonical UTC ISO `startsAt`/`endsAt`, and `retentionYears: 1`. Unknown fields, control characters, invalid contact/date values and non-increasing dates fail closed. CUP edits times in Moscow and converts them to UTC. LK shows the notice in Moscow, including purpose, responsible person, contact, retention deadline and public ranking fields. This is a notice, with no claim to record a separate legal consent or marketing subscription. No email is sent.

Registration can open before `startsAt`, but only with valid policy and before `endsAt`. Start/finish require `startsAt <= serverNow < endsAt`, without a finish grace period. Ranking remains readable to eligible registered members until the exact retention deadline. One calendar year uses the UTC anniversary, clamping 29 February to 28 February. At/after the deadline ranking returns 410 `EVENT_DATA_EXPIRED`. Blocking a read does not physically delete data.

The form submits `policyRevision`; direct/invite errors return a validated public `eventNotice` so an invitation does not show a blind form. Stored registration binds epoch + type-settings revision + notice version and server-derived `retentionUntil`. Changing settings requires a new registration; the replaced participant entry also starts a new best-score record. Old clients without the revision cannot bypass the notice. Deploy compatible LK and CUP together before activation.

The LK repository runbook `docs/event-community-launch-preparation.md` describes pilot preparation and guarded erasure. These source tools never deploy, connect to MongoDB, create the community or collect real participant data.
