# Изменения канонического уровня игрока

В ЦУП откройте «Уровни», найдите игрока и выберите «Изменить уровень». Число от 1 до 7
хранится с точностью до пяти знаков. Букву определяет шкала ЦУП. Комментарий обязателен.
Для существующего игрока команда требует подтверждённый `clientId` в канонической записи.

Уровень действует во всех станциях. Для поиска, карточки и истории нужен глобальный
`player-ratings:read`. Изменение требует отдельно выданного глобального `player-ratings:write`.
Роли с ограничением по станциям получают отказ. Проверяется эффективная область конкретного
права из сессии. Редактирование уровня не выдаёт и не меняет права сотрудника.

Журнал изменений доступен из «Уровней» и из общего журнала сотрудников при глобальном
`audit:read` и `player-ratings:read`. Есть фильтры по ID сотрудника и игрока, действию и датам
по Москве. Время в файлах записано в UTC. Выгрузка страницы фиксирует ID и порядок показанных
записей. Выгрузка по фильтрам возвращает весь результат до 5 000 записей. Для большего объёма
нужно сузить фильтры. CSV экранирует формулы, XLSX сериализует комментарии в текстовые ячейки.

Запись уровня, событие и задание проекции ЛК2 записываются в одной транзакции MongoDB.
Повтор того же тела с тем же ключом и автором возвращает исходное событие. Подмена команды
с тем же ключом отклоняется. Для аудита уровней открыты только чтение и экспорт.
История сохраняет прежние записи `CUP_ADMIN` и отображает их как `ADMIN_MANUAL`.

Результат игры открывается по точному ID и ревизии счёта. Результат турнира открывает
снимок расчёта для конкретного игрока с ID и ревизией протокола. Для исторической строки
с неполной ссылкой сохраняются доступные сведения об источнике. Импорты и служебные сверки
сохраняют своё происхождение.

## Совместимость выпуска

Черновик использует общий кандидат канонических уровней. ЛК1 читает тот же
`player_rating_state`. ЛК2 применяет существующий ревизионный контракт к связанному
`clientId` через `player_level_projection_outbox`. Покрытие определяется разрешённым
контуром отправителя, его конфигурацией и связью профиля в ЛК2.

До включения редактирования нужны все три согласованных кандидата, транзакции MongoDB,
включённая проекция для утверждённой области и действующая синхронизация ЛК2.
Проверить инструкции по каноническому уровню и совместимости исторического комплекта
восстановления ЦУП. Затем на отдельном стенде повторить изменение, сверить обе проекции,
ссылку на версию результата и CSV/XLSX. Политики прав и параметры подключения утверждаются
отдельно для целевого окружения.

При переключении на исторический комплект восстановления сначала закрыть на входе старые
маршруты изменения и повтора проекции. Устаревший отправитель уровня в Viva должен быть выключен.
Доставку в ЛК2 приостанавливать только при необходимости.
Историю и накопленные задания сохранять. После первой ручной записи нельзя возвращать
старую логику воспроизведения журнала без сверки состояния. Этой задачей не требуется
перезаписывать старые записи или применять миграцию MongoDB.
