# Изменения канонического уровня игрока

В ЦУП откройте «Уровни», найдите игрока и выберите «Изменить уровень». Число от 1 до 7
хранится с точностью до пяти знаков. Букву определяет шкала ЦУП. Комментарий обязателен.
Для существующего игрока команда требует подтверждённый `clientId` в канонической записи.

Уровень один для всех станций. Проверяется эффективная область конкретного права из сессии:
станции учётной записи пересекаются со станциями ролей, выдающих право. Пустое пересечение
означает отказ. Редактирование уровня не выдаёт и не меняет права сотрудника.

- Поиск, карточка, история и ссылка на результат игры или турнира требуют `player-ratings:read`
  с любой непустой областью.
- Изменение требует `player-ratings:write`. Сотрудник станции меняет общий уровень от имени
  станции из своей области, и событие хранит `actor.stationId`. При одной станции она
  подставляется сама. При нескольких станциях её выбирают в форме, иначе возвращается
  `RATING_STATION_REQUIRED`. Чужая станция получает отказ 403. Глобальный сотрудник может
  указать станцию или не указывать её («все станции»). Повтор с тем же ключом от другой
  станции считается другой командой и отклоняется (409).
- По умолчанию `player-ratings:write` выдан ролям «Управляющий» и «Админ станции»,
  а `player-ratings:read` есть и у «Админа станции». Сохранённые системные роли не меняются
  сами: в развёрнутой среде право добавляют в «Роли и права» отдельно.
- Учётная запись без привязки к станциям на такой роли редактирует уровни и видит журнал
  всех станций. Это решение владельца от 2026-11-19.
- Права решают сохранённые роли с первого запроса после старта. ЦУП ждёт подключения
  MongoDB прав до загрузки ролей. Значения по умолчанию используются, только если хранилище
  прав не настроено или недоступно.
- При подключённом хранилище `player-ratings:write` берётся только из сохранённой роли.
  Системная роль, которой нет в MongoDB или которая сохранена без списка прав, получает права
  по умолчанию без него.
- Если хранилище прав настроено (`MONGODB_URI`), но недоступно, изменение уровня не выполняется
  ни для кого: сессия не получает `player-ratings:write`, а запись отвечает 503
  `STAFF_RIGHTS_UNCONFIRMED`. ЦУП переподключается к хранилищу на запросах не чаще раза в
  `ADMIN_AUTH_RECONNECT_INTERVAL_MS` (5 000 мс) и после восстановления применяет сохранённые роли.

Журнал изменений доступен из «Уровней» и из общего журнала сотрудников при `audit:read` и
`player-ratings:read`. Глобальные права на оба действия показывают журнал всех станций. При
ограничении по станциям видны только правки, сделанные от станций, общих для обоих прав.
Прежние правки без станции видны только глобальному сотруднику. «Админ станции» по умолчанию
не имеет `audit:read` и журнала не видит. В CSV/XLSX есть колонка «Станция». Есть фильтры по ID сотрудника и игрока, действию и датам
по Москве. Время в файлах записано в UTC. Выгрузка страницы фиксирует ID и порядок показанных
записей. Выгрузка по фильтрам возвращает весь результат до 5 000 записей. Для большего объёма
нужно сузить фильтры. CSV экранирует формулы, XLSX сериализует комментарии в текстовые ячейки.

Запись уровня, событие и задание проекции ЛК2 записываются в одной транзакции MongoDB.
Повтор того же тела с тем же ключом и автором возвращает исходное событие. Подмена команды
с тем же ключом отклоняется. Для аудита уровней открыты только чтение и экспорт.
История сохраняет прежние записи `CUP_ADMIN` и отображает их как `ADMIN_MANUAL`.

Результат игры открывается по точному ID и ревизии счёта. Результат турнира открывает
снимок расчёта для конкретного игрока с ID и ревизией протокола. Для исторической строки
с неполной ссылкой сохраняются доступные сведения об источнике. Импорты и служебные сверки
сохраняют своё происхождение.

## Совместимость выпуска

Итоговый манифест общего комплекта — `docs/release/cup133-joint-release-manifest.json`. В нём точные
коммиты ЦУП, ЛК1 и ЛК2, runtime-артефакт ЦУП, оба воркера ЛК1 (64 файла релиза с дайджестом),
модуль уровня, файлы отправителя и приёмника проекции, обязательные входы фронтенда и графа Node-RED
и порядок восстановления. Сверка только читает чекауты и локальные артефакты:
`node scripts/verify-cup133-joint-release-manifest.mjs --cup <dir> --lk1 <dir> --lk2 <dir> [--artifacts <dir>]`.
Поле `releaseComplete` равно `true`, когда записаны хеши выдаваемого фронтенда и итогового графа. Перед импортом
граф 147 читается заново: если его SHA-256 изменился, итоговый граф пересобирается.

Черновик использует общий кандидат канонических уровней. ЛК1 читает тот же
`player_rating_state`. ЛК2 применяет существующий ревизионный контракт к связанному
`clientId` через `player_level_projection_outbox`. Покрытие определяется разрешённым
контуром отправителя, его конфигурацией и связью профиля в ЛК2.

До включения редактирования нужны все три согласованных кандидата, транзакции MongoDB,
включённая проекция для утверждённой области и действующая синхронизация ЛК2.
Проверить инструкции по каноническому уровню и совместимости исторического комплекта
восстановления ЦУП. Затем на отдельном стенде повторить изменение, сверить обе проекции,
ссылку на версию результата и CSV/XLSX. Политики прав и параметры подключения утверждаются
отдельно для целевого окружения.

При переключении на исторический комплект восстановления сначала закрыть на входе старые
маршруты изменения и повтора проекции. Устаревший отправитель уровня в Viva должен быть выключен.
Доставку в ЛК2 приостанавливать только при необходимости.
Историю и накопленные задания сохранять. После первой ручной записи нельзя возвращать
старую логику воспроизведения журнала без сверки состояния. Этой задачей не требуется
перезаписывать старые записи или применять миграцию MongoDB.
