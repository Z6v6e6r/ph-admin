# Explicit tournament organizer assignment (source contract v1)

This packet assigns or revokes one **canonical PadlHub user UUID** on an existing CUP LOCAL_ONLY custom tournament. No creator, telephone, mechanics manager or display name implies organizer authority. This does not enable tournament chat, confer existing chat access, or establish an ongoing ACTIVE-user entitlement. A future chat owner must check current assignment and current canonical identity independently.

## Identity lookup

CUP calls only `POST /internal/api/v1/:tenantKey/tournament-organizer-profile-lookups`. Exact JSON fields in serialization order: `contractVersion:1`, `requestId`, `assignmentOperationId`, `tournamentId`, `selectedUserId`, `expectedAssignmentRevision`. UUIDs are lowercase canonical UUIDs; revision is a nonnegative safe integer. `tournamentId` is the existing public tournament UUID projection, not the CUP raw ID. The signed SHA256 is over UTF-8 JSON in that order.

Dedicated RS256 header: `alg:RS256`, `typ:phub-tournament-organizer-lookup+jwt`, configured `kid`. Exact claims: `contract_version:1`, `iss`, `aud`, `sub` (CUP service, not a user), `scope:tournaments.organizer-profile.read`, `tenant_id`, `tenant_key`, `method:POST`, exact `path`, `request_sha256`, UUID `correlation_id`, UUID `jti`, integer `iat`, `nbf=iat`, `exp`. Lifetime 1–30 seconds; no clock grace. Other user/client/subscription tokens, extra claims, wrong tenant/purpose/key/body/path and query strings are rejected. Redis `SET NX EX` claims a tenant/key/purpose scoped nonce before any profile query. Redis failure fails closed. Redis loss may permit repeating this **read-only** lookup during the original short lifetime; this is neither assignment nor send authority.

The SQL read uses the canonical tenant and ACTIVE `identity.users` row, minimal profile summary, exactly one synchronized `VIVA/viva_profile` mapping in both directions, and one VIVA `integration.identity_provider_bindings` row. Existing database constraints disallow duplicate canonical mappings/bindings; defensive bounded selection rejects ambiguity. No phone/name matching. The response echoes every input field, canonical `tenantId/tenantKey`, `profile:{userId,displayName}`, private `ownerTenantKey`, `checkedAt`, and the original signed `expiresAt`. CUP checks all bindings again. No client/mapping ID, telephone or avatar is returned. `ownerTenantKey` is integration-only and is removed from browser responses.

## Atomic owner and recovery

Staff endpoints under `/tournaments/custom/:id/organizer` use the existing CUP tournament ID route convention: GET current; POST `preview`; POST `operations`; GET `operations/:operationId`. Write and read require verified staff-token identity, `tournaments:write`, and its existing station scope. The browser command is exactly `{contractVersion:1,operationId,action:ASSIGN|REVOKE,selectedUserId:UUID|null,expectedRevision}`. `Idempotency-Key` equals operationId and correlation is a UUID. Preview is never an assignment proof; ASSIGN resolves again server-side.

The first durable **full raw tournament-document CAS** binds the operation UUID, exact body hash, staff principal, canonical tenant, private owner namespace, resulting assignment revision and audit receipt. No prelookup reservation exists. Failed lookup/timeout before CAS is not a terminal operation receipt. CAS zero or ambiguous ACK performs an exact original read, never a write with a refreshed revision. GET never creates a command, runs lookup, or mutates state.

An ASSIGN uses the same signed expiry through the client response, local prewrite check `expiry > localNow + 5000ms` and Mongo `$$NOW < expiry - 5000ms` predicate, sharing the named 5000ms CAS execution budget/maxTimeMS. The stored receipt retains the original signed expiry unchanged. The readonly lookup is an observation, not a cross-database lock: identity can become disabled after lookup. This is authorization freshness at the owner operation clock plus a reserved execution budget, not a hard durability-ACK deadline or a cross-database clock proof. Mongo $$NOW is stable per operation and maxTimeMS interruption is not a real-time scheduler guarantee. Accurate bounded server clocks are an activation prerequisite; the Mongo and CUP checks do not prove synchronized production clocks. A historical receipt never expires into fresh execution. After later revoke/reassign, replay returns original `operation.resultingRevision/resultingSelectedUserId` separately from `current`. Staff responses include canonical `tenantId` and `tournamentId`; the original receipt additionally echoes stored `expectedRevision` and `requestedSelectedUserId`. The editor checks all original fields and saved tenant/tournament UUIDs before clearing custody, including REJECTED receipts. Current staff/station and configured namespace are checked before replay disclosure. Only exact original body/staff replay ignores stale expectedRevision. Stale commands that are durably receipted return REJECTED with unchanged current state.

Private `tournamentOrganizerV1` stores one assignment and at most 128 permanent receipts, never evicted. One remaining slot is reserved while an organizer is assigned so a current-revision REVOKE remains possible. Saturation stops new assignment; no automatic reset, retention purge or ID reuse is allowed. Mongo document-size/headroom and competing writer inventory remain activation checks. `localParticipationOperations` retains its separate 512-entry guard and original generations. JOIN/LEAVE full-row CAS serializes with assignment and preserves the organizer field. REVOKE on an adopted row needs no profile lookup, remains available with lookup disabled and after archive/type changes, and still checks current staff/namespace. An unadopted no-organizer REVOKE does not create custody.

Generic `updateCustomTournament` retains its original local-participation guard. Before first JOIN, organizer-adopted documents use full raw preimage CAS and the existing whitelist `$set`, preserving private custody. A stale edit cannot cross adoption or assignment. Existing restore and legacy roster/payment writers reject organizer-field **presence**, independent of flags/type, including malformed markers. Those legacy operations remain unavailable after adoption; LOCAL_ONLY owner JOIN/LEAVE and organizer revoke are the supported scoped writers. No generic writer may reset the marker or journal. Current public tournament projections/export omit all private assignment/journal/owner-namespace data; only the staff organizer endpoint exposes canonical assignment state.

## Browser custody

The CUP editor accepts explicit UUID input, displays the server preview, and offers assign/revoke and original-status read. Before POST it stores bounded metadata (the exact UUID command, canonical tenant/tournament UUIDs, staff/API/tournament scope) in same-tab sessionStorage, at most 16 unresolved tournament operations, no eviction. Reload/reopen calls GET original status only. UNKNOWN, timeout, malformed reply, 401/403/404 retain custody; access denial hides cached preview/current state. No automatic POST, fresh UUID, body replacement or blind retry occurs. A confirmed exact receipt is the only normal custody-clear event. Closing/logout invalidates callbacks, including late ACK. Storage failure blocks dispatch. SessionStorage/tab loss can lose local recovery metadata; server receipts remain permanent. Closing a tab is not evidence of no mutation.

## Disabled configuration and rollout limits

Both sides use dedicated `TOURNAMENT_ORGANIZER_LOOKUP_*` namespaces: ENABLED (default false), TENANT_ID, TENANT_KEY, ISSUER, AUDIENCE, SUBJECT. LK2 additionally PUBLIC_KEYS_FILE (bounded JSON kid→RSA public PEM); CUP additionally BASE_URL (HTTPS origin only), KEY_ID, PRIVATE_KEY_FILE. RSA minimum 2048 bits. CUP requires explicit existing `LK_IDENTITY_EXPECTED_TENANT_KEY`, compares it with lookup-derived `ownerTenantKey` and existing `localParticipationTenantKey`, and persists that binding. Canonical tenant key and provider tenant key may deliberately differ. No default tenant is guessed. Keep tenant authorization configuration available for read/revoke when lookup signing is disabled. Configuration examples are names only; no credentials are created or installed by this packet.

Lookup client: one request, 3s network/body timeout, 4KiB response cap, no redirects or retry; three dependency failures open a 10s breaker. Access/input denials do not poison that shared breaker. Metrics are fixed redacted outcome counters; no body, profile/provider IDs, Bearer or private key logs. LK2 SQL statement timeout 2s; nonce timeout 1.5s; existing API rate limiting and pool bounds remain in force.

SOURCE/LOCAL tests are not installation or authorization evidence. Pairing/installation, credential provisioning, existing-writer drain, majority-durable Mongo setup, clock bounds, storage capacity, real profile mapping completeness and actual provider/runtime behavior require separate approved checks. No new collection, index, TTL, migration, key, workflow dispatch, chat send or live write is part of this task. Physical Mongo7 and migrated PostgreSQL suites run only in existing guarded CI fixtures; no local database has been provisioned.
