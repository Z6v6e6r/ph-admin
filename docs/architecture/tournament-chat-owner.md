## Authority and compatibility

The current LOCAL_ONLY raw tournament, original JOIN journal and current explicit organizer journal are the only access source. An ACTIVE canonical LK2 session and unique valid provider mapping must be verified by the future LK2 caller before issuing the dedicated assertion. CUP uses its signed provider tuple to resolve exactly one original REGISTERED generation, no matching LEFT, and one exact roster generation/original receipt phone/REGISTERED/UNPAID row. A phone match alone, waitlist, creator or mechanics manager grants nothing. Otherwise current explicit canonical organizer UUID may authorize. When both apply, first candidate chooses PARTICIPANT. Retries retain that original kind/generation or organizer revision; they never switch to another authority or refreshed generation. The chosen original authority must still hold at acceptance.

Current LOCAL_ONLY PLANNED/REGISTRATION/RUNNING/FINISHED participants and organizer can read/send. CANCELED, archived, provider-bound or unsupported records deny new access. This mirrors current LK2 GAME messaging, where cancellation denies but finishing does not revoke active participation. Accepted recovery deliberately works after cancellation/archive/type change, LEFT or REVOKE; disclosure still requires current access. Session revocation/user disablement is checked by LK2 before issuing each assertion, with a maximum 30-second assertion window, not an atomic cross-database revocation promise.

## Private wire and actor assertion

Canonical controller paths (an existing external proxy may prepend `/api`):

* POST `/internal/tournaments/chat/v1/message-requests`: `{contractVersion:1,tournamentId,requestId,text}`. UUIDs lower-case canonical, exact text 1..8000 UTF-16 units, max32000 UTF-8 bytes, valid UTF-8 round trip, no NUL, not whitespace-only. `Idempotency-Key` equals requestId.
* POST `/internal/tournaments/chat/v1/message-requests/read`: `{contractVersion:1,tournamentId,requestId}`. Read-only: never creates a candidate, accepts, publishes or runs recovery.
* POST `/internal/tournaments/chat/v1/history`: `{contractVersion:1,tournamentId,limit,cursor?}`, limit1..50. Read-only. LK2 public GET wrappers are separate adoption work.

`bodyBytes` serializes these exact parsed keys in the order above using JSON.stringify. The assertion binds that canonical representation, not arbitrary incoming object key order. An assertion for one of these paths cannot be used at another. No URL, source selector, actor or verified result comes from the browser.

JWT header exactly `{alg:'RS256',typ:'phub-tournament-chat-actor+jwt',kid}`. Claims exactly `contract_version:1,iss,aud:'cup-tournament-chat-v1',sub:<canonical user UUID>,scope:'tournaments.chat.actor',tenant_id,tenant_key,owner_tenant_key,provider_client_id,session_id,method:'POST',path,request_sha256,correlation_id,jti,iat,nbf,exp`. `nbf===iat`, TTL<=30s, future issuance/expired proof denied. Dedicated issuer/public key only; organizer lookup, subscription, browser user and CUP staff credentials are not accepted. Provider fields never appear in response, logs or public clients.

No Redis nonce is used: replay is precisely the same signed operation/body and permanent first-wins document; current access is rechecked. Nonce loss must not become write authority. Fresh retry may carry a fresh assertion for the same original request, but never refresh candidate authority/body. Before bootstrap/acceptance require local now+5000ms < signed expiry, plus Mongo `$$NOW < expiry-5000ms`, maxTimeMS5000. Confirmed response: `{contractVersion:'tournament-chat.v1',tournamentId,requestId,status:'CONFIRMED',requestHash,streamId,messageId,sequence}`. `requestHash=digest('tournament-chat-request:v1', parsedSend)` using the existing SHA256(domain + NUL + JSON.stringify(value)) convention. ## Durable custody and publication

1. Read original per-request `_id` FIRST, before generating server UUIDs or resolving a new candidate witness. Existing immutable server fields are reused; changed body/identity/incarnation conflicts.
2. If no candidate and no stream, full raw tournament CAS adopts permanent random streamId and bootstrap audit under current ACL/fresh proof. ACK loss reads the durable marker; it never resets an existing stream. Adoption is not message acceptance. Candidate insert failure leaves the marker intact.
3. Dedicated `tournament_chat_requests_v1` document: builtin unique string `_id` is SHA256 of domain plus [canonical tenant,tournament UUID,actor UUID,request UUID]. Immutable core stores exact request/hash, public messageUUID, private typed raw-incarnation hash, stream, canonical actor/provider actorHash and original chosen witness. First-wins insert/readback never rebinds it. No TTL/deletion/eviction, including uncertain candidates.
4. Full raw tournament CAS is acceptance: append exact coreHash/ref + acceptedAt/canonical actor/correlation/audit; allocate next safe sequence. Permanent `tournamentChatV1` includes version/tenant/provider namespace/tournament/incarnation/stream, allocatedSequence, publishedSequence, pendingCount and pending refs, bootstrap audit. pendingCount equals pending.length; cap64, sequence range below Number.MAX_SAFE_INTEGER. Saturation refuses NEW intents before candidate insert, never removes custody or blocks JOIN/LEAVE/REVOKE. A concurrent CAS miss is UNKNOWN; an explicit original retry can use a new unrelated raw preimage only while its captured witness still holds.
5. Recovery operates on the oldest accepted ref only. It durably adds an exact publication receipt to its candidate using document CAS and majority readback; then full raw tournament CAS advances contiguous publishedSequence/removes that ref. Intermediate publication is hidden by the frontier. Missing/malformed candidate, ACK loss or CAS miss retains custody. Another worker may recover the exact same operation; it cannot skip a hole. Publication/acceptance use the same stable message UUID.
6. History/status check fresh current ACL after storage reads. Publication record alone is not CONFIRMED; same stream/incarnation and durable frontier must prove visibility. Recovery does not need a fresh user token or current membership.

Recovery service uses the existing tournament Mongo client, one nonoverlapping bounded cycle, up to4 persisted pending targets and one intent per target, every15s when explicitly enabled. Queries have maxTimeMS, all writes majority+journaled with5s budget. Fixed redacted counters/warnings distinguish partial/unavailable recovery; no message body, Bearer or private IDs in diagnostics. This is source scheduling, not evidence of an installed worker/latency SLA. A corrupt target can remain pending indefinitely; activation must size throughput and operational handling without deleting custody.
